# WFL-003 slice A: bounded AI step execution and admin dry run

Date: 2026-09-12. Base: `main@489eb41` (branch line d63e39a + r3 fixes).

## What exists now

- `workflow_steps.py`: `run_ai_steps(workflow, context, provider)` executes
  `ai_compose` and `ai_classify` steps in document order, one provider call
  per step, each under its own 60 s deadline, with no retry. `StepContext` is a
  closed, bounded record (workflow name, event, HH:MM time, at most 20 string
  states of at most 255 characters) rendered deterministically into the user
  message after the step prompt; nothing is read from Home Assistant.
  Compose replies must be non-empty text of at most 2,000 characters with no
  tool calls or structured output. Classify requests a structured output whose
  only property is `category` with an `enum` of the step's categories, and
  accepts only exactly that shape with a listed category. Anything else is a
  static `invalid_output` failure; the first failure stops the run and later
  steps are `skipped`. `notify` is never executed; it is reported `planned`
  with the id of the step whose text it would use. `actions_executed` is 0 by
  construction.
- `workflow_dry_run_api.py`: admin-only `ai_orchestrator/workflows/dry_run`
  (`workflow_id`, local `connection_id`, `snapshot_json` ≤ 131,072 chars).
  Requires a loaded foundation and a ready store; evaluates the stored
  document offline with `preview_workflow` first and returns early with no
  provider call when the scenario is not eligible. The model context includes
  only the states of entities the workflow's own conditions name, mirroring the
  live observer's bound. One dry run per administrator at a time; provider
  unload or change during the run is reported, not silently returned. Results
  are returned to the caller and retained nowhere.
- `WorkflowManager.get(workflow_id)` accessor; new runtime set
  `workflow_dry_runs_in_progress`; command registered in `websocket_api.py`.
